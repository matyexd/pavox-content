# Telegram Bot: текущее состояние и план

## Задача

Сервис получает публикации из Telegram-канала магазина Pavox и постепенно преобразует их в данные, пригодные для дальнейшей обработки, проверки и создания материалов в Strapi.

На текущем этапе мы сознательно используем `getUpdates` и long polling. Это позволяет запускать сервис локально без публичного HTTP-сервера и webhook.

## Как Telegram доставляет данные

Ответ `getUpdates` имеет общую оболочку:

```text
TelegramResponse[[]Update]
├── OK
├── Description
├── ErrorCode
└── Result []Update
```

Каждый `Update` — отдельное событие Telegram:

```text
Update
├── UpdateID
└── ChannelPost
```

`UpdateID` используется для подтверждения обработки через параметр `offset`. После успешной обработки update со значением `N` следующий запрос может передать `offset=N+1`. Это означает, что updates с меньшими ID уже обработаны; это не предположение о том, что ID всегда идут без пропусков.

## Текст, фотография и подпись

У обычного текстового сообщения заполнено поле `ChannelPost.Text`.

У сообщения с фотографией текст находится в `ChannelPost.Caption`, а поле `Photo` содержит не разные фотографии, а несколько размеров одной фотографии:

```text
Photo[0] → маленький размер
Photo[1] → средний размер
Photo[N] → самый большой размер
```

Для скачивания выбирается последний элемент `Photo`, предварительно проверяется, что slice не пустой.

## Получение файла

Скачивание фотографии состоит из двух HTTP-запросов.

Сначала по `file_id` вызывается метод `getFile`:

```text
GET /bot<TOKEN>/getFile?file_id=<FILE_ID>
```

Он возвращает JSON с объектом `TelegramFile`, в том числе с полем `file_path`.

Затем бинарное содержимое скачивается по адресу:

```text
GET /file/bot<TOKEN>/<FILE_PATH>
```

Второй запрос возвращает не JSON, а поток байтов. Он копируется в `io.Writer` через `io.Copy`, поэтому изображение не нужно целиком загружать в память.

Для бинарного ответа проверяется HTTP-статус, а JSON-ответ Telegram дополнительно проверяется через поле `OK`. `response.Body` закрывается через `defer` после успешного `http.Get`.

## Конфигурация и секреты

Telegram-токен читается из переменной окружения:

```text
TELEGRAM_BOT_TOKEN
```

Локально переменная загружается из игнорируемого файла `.env`:

```sh
source .env
```

Токен хранится внутри одного экземпляра `TelegramClient`, а не в глобальной переменной. Методы клиента используют один и тот же токен для `getUpdates`, `getFile` и скачивания файлов.

Настоящий токен нельзя записывать в исходный код, README, логи или Git.

## Generic-ответ Telegram

Telegram использует общую JSON-оболочку, но тип поля `result` зависит от метода. Поэтому определён generic-тип:

```go
type TelegramResponse[T any] struct {
	OK          bool   `json:"ok"`
	Result      T      `json:"result"`
	Description string `json:"description"`
	ErrorCode   int    `json:"error_code"`
}
```

Примеры конкретных типов:

```text
getUpdates → TelegramResponse[[]Update]
getFile    → TelegramResponse[TelegramFile]
```

Generic-функция HTTP-запроса получает тип результата явно:

```text
telegramRequest[[]Update](url)
telegramRequest[TelegramFile](url)
```

## Обработка ошибок и ресурсов

Нижний уровень возвращает ошибки вызывающему коду, а не принимает решение о завершении процесса самостоятельно.

Дополнительный контекст добавляется через `%w`:

```go
fmt.Errorf("download file: %w", err)
```

Локальный файл закрывается после завершения скачивания. Ошибки скачивания и закрытия проверяются отдельно.

`offset` должен обновляться только после успешной обработки. Если обработка update завершилась ошибкой, текущая пачка прерывается, чтобы Telegram мог вернуть необработанные данные повторно.

## Альбомы и `media_group_id`

Альбом, который пользователь видит как одну публикацию, Telegram Bot API присылает как несколько `Update`:

```text
Update 1 ─┐
Update 2 ─┼─ одинаковый media_group_id
Update 3 ─┘
```

Каждый update содержит одну фотографию в нескольких размерах. Caption обычно присутствует только у одного сообщения группы.

Для внутренней модели определён `TelegramPost`:

```text
TelegramPost
├── Text
├── Caption
├── MediaGroupID
├── Photos
└── UpdateIDs
```

Текущая функция группировки:

- объединяет одинаковые `media_group_id`;
- оставляет одиночные updates отдельными;
- сохраняет порядок первого появления;
- выбирает максимальный размер каждой фотографии;
- сохраняет первый непустой `Text` и `Caption`;
- собирает все входящие `UpdateID`.

Для одиночных сообщений используется внутренний ключ вида `single:<update_id>`. Он нужен только для `map` и не записывается в итоговый `MediaGroupID`.

### Текущее ограничение

Группировка работает только внутри одного ответа `getUpdates`. Telegram предоставляет `media_group_id`, но не сообщает размер группы и не помечает последнюю часть альбома. Поэтому для группировки между несколькими запросами позже понадобится временный буфер и период ожидания новых элементов.

## Тесты

Для преобразования updates написаны unit-тесты. Они проверяют:

- одиночный текстовый пост;
- альбом из нескольких фотографий;
- первый непустой caption;
- выбор максимального размера изображения;
- список `UpdateIDs`;
- порядок смешанной пачки: одиночный пост, альбом, одиночный пост.

Тесты запускаются командой:

```sh
go test -v ./...
```

## Текущее устройство файлов

```text
main.go              polling и управление offset
telegram_api.go      методы TelegramClient
telegram_types.go    DTO Telegram и TelegramPost
processor.go         обработка update и группировка
processor_test.go    тесты группировки
utils.go             HTTP/JSON helpers
```

Пока все файлы находятся в одном `package main`. Go компилирует файлы одной папки и одного пакета вместе, поэтому между ними не нужны импорты. Выделение отдельного пакета `internal/telegram` будет оправдано, когда публичная граница клиента стабилизируется и появится необходимость независимо тестировать Telegram transport.

## Ближайший план

1. Переименовать текущую функцию преобразования `processPost([]Update)` в `groupUpdates([]Update)` и обновить тесты.
2. Создать отдельную обработку `processPost(client, TelegramPost) error`.
3. Подключить цепочку `getUpdates → groupUpdates → processPost` в `main`.
4. Обновлять `offset` только после успешной обработки всей полученной пачки.
5. Добавить тесты ошибок и пустого входного slice.
6. Определить отдельную директорию для скачанных файлов и правила её очистки.
